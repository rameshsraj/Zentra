## CHANGE-1: Agent Component Discovery — Full Rework

**Area:** Agent → Component Discovery  
**Type:** Bug Fix + Enhancement

### Context
The agent's component discovery mechanism was broken. When the agent scanned the host for running middleware (nginx, apache, redis, etc.), it was either not reporting components at all or reporting them with wrong metadata. The API side had no proper endpoint to receive and persist discovered components, causing the Fleet page to show blank component lists.

### What Was Done
- Rewrote the component discovery loop to detect running processes and open ports for all supported middleware types (nginx, apache, haproxy, redis, memcached, kafka, elasticsearch, etc.)
- Fixed the discovery report payload to include `host`, `port`, `instance_type`, `name`, and `version` fields
- Added deduplication logic using a unique constraint on `(agent_id, instance_type, host, port)` to prevent duplicate discoveries on each poll
- Updated the API handler to upsert discovered components into `middleware_instances` automatically when an agent reports them
- Added a new DB migration to add the unique constraint on the `discovered_components` table

### Acceptance Criteria
- [ ] Agent reports discovered components every 5 minutes
- [ ] API stores them without duplicates
- [ ] Fleet page shows all discovered middleware for each agent

## CHANGE-3: Agent API Key Authentication — Fix Auth Middleware

**Area:** API → Auth Middleware  
**Type:** Bug Fix

### Context
The agent was sending its API key in the `X-Agent-Key` header, but the auth middleware was checking `Authorization: Bearer` only. This caused all agent API calls (metric push, heartbeat, component discovery) to return 401 Unauthorized.

### What Was Done
- Updated auth middleware to accept keys from both `Authorization: Bearer <key>` and `X-Agent-Key: <key>` headers
- Added a separate lookup path for agent keys (prefixed `isok_`) vs user session tokens
- Fixed the routes that require agent-level auth vs user-level auth

### Acceptance Criteria
- [ ] Agent heartbeat returns 200 with valid `X-Agent-Key`
- [ ] Agent metric push returns 200
- [ ] User session tokens still work on all user-facing routes

## CHANGE-8: Server Plugin — Middleware Collector (nginx, apache, redis, memcached)

**Area:** Agent → Server Plugin → Middleware Collector  
**Type:** Bug Fix + Enhancement

### Context
The middleware collector in the server plugin was non-functional for several key types:
- **nginx** and **apache**: The collector attempted Prometheus exporter endpoints on native ports, always getting 404s. It was also recording `reachable=0` instead of real metrics.
- **redis** and **memcached**: Same issue — scraping `/metrics` on native ports instead of using native protocols.
- The collector had no fallback handling when status modules were not enabled.

### What Was Done
- **nginx**: Updated to scrape the native `stub_status` endpoint (`/nginx_status`). Added fallback paths (`/stub_status`, `localhost` vs configured IP). Returns `reachable=1` gracefully when the module is not enabled.
- **apache**: Updated to scrape `/server-status?auto`. Added localhost-first fallback. Returns `reachable=1` gracefully when `mod_status` is not enabled.
- **redis**: Replaced HTTP scraping with native TCP `INFO` command. Parses `connected_clients`, `used_memory`, `instantaneous_ops_per_sec`, `keyspace_hits/misses` and computes hit rate.
- **memcached**: Replaced HTTP scraping with native TCP `stats` command. Parses all standard stat fields and computes hit rate.
- Added haproxy, elasticsearch collectors with proper endpoint scraping.

### Acceptance Criteria
- [ ] `nginx.active_connections`, `nginx.requests`, `nginx.waiting` appear in metrics table
- [ ] `apache.busy_workers`, `apache.requests_per_sec`, `apache.bytes_per_sec` appear in metrics table
- [ ] `redis.ops_per_sec`, `redis.used_memory_mb`, `redis.hit_rate` appear in metrics table
- [ ] `memcached.curr_items`, `memcached.hit_rate`, `memcached.bytes_used_mb` appear in metrics table

## CHANGE-9: API Middleware Handlers — Redis Collection Fix

**Area:** API → Middleware Handlers → Redis  
**Type:** Bug Fix

### Context
The Redis status handler in the API was scraping a Prometheus `/metrics` endpoint on the Redis native port (`6379`), which always returned 404. No real Redis metrics were ever collected.

### What Was Done
- Replaced the Prometheus scrape with a native TCP connection sending the `INFO` command
- Parses the Redis INFO response for: `connected_clients`, `used_memory`, `instantaneous_ops_per_sec`, `keyspace_hits`, `keyspace_misses`, `uptime_in_seconds`, `redis_version`
- Computes `hit_rate = hits / (hits + misses) * 100`
- Saves all 4 key metrics to `middleware_metrics` per poll for historical charting

### Acceptance Criteria
- [ ] Redis status endpoint returns real data instead of zeros
- [ ] History charts show `ops_per_sec`, `used_memory_mb`, `connected_clients`, `hit_rate`

## CHANGE-14: Nginx stub_status & Apache mod_status — Enable on Target Server

**Area:** Server Configuration (target host)  
**Type:** Enhancement

### Context
Even after fixing ports, both status endpoints returned `404` because the modules were not enabled. `nginx_status` requires `stub_status` to be configured in a `location` block; Apache requires a `<Location /server-status>` block with `mod_status`.

### What Was Done
- Added `location /nginx_status { stub_status on; }` to the nginx server block on port `8081`
- Created an Apache config file with `<Location /server-status>`, `SetHandler server-status`, `ExtendedStatus On`
- Verified both endpoints return live data after config reload

### Acceptance Criteria
- [ ] `curl http://<host>:8081/nginx_status` returns `Active connections: N`
- [ ] `curl http://<host>:8080/server-status?auto` returns key-value pairs
- [ ] Metrics start flowing into the DB within one collection cycle
